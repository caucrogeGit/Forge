Forge IoT et Forge Video.

Forge IoT

Module opt-in pour recevoir, stocker et exposer des données de capteurs : un subscriber MQTT alimente la table iot_events, relue via une API HTTP JSON.
Le core reste autonome.

  • # Diagnostic du module IoT$forge iot:doctor
  • # Copie la migration de la table iot_events$forge iot:init
  • # Subscriber MQTT résilient$forge iot:listen
  • # Capteurs simulés pour tester sans matériel$forge iot:simulate

Forge Video

Module opt-in pour l'upload, le transcodage MP4 (H.264/AAC) et la lecture en streaming (HTTP Range).
Le transcodage se fait dans un worker CLI, jamais pendant une requête.

  • # Entrée d'upload officielle d'une vidéo$forge video:upload
  • # Worker de transcodage MP4 + poster$forge video:process
  • # Purge des vidéos en échec et fichiers orphelins (dry-run par défaut)$forge video:cleanup
  • # Diagnostic du module vidéo$forge video:doctor

Installer Forge selon votre usage.

Poste Windows 10/11 pro

Windows + WSL

Parcours complet : WSL Ubuntu 24.04, VS Code Remote WSL, pipx, Node.js 20, MariaDB avec compte forge_admin.

Sur un poste Windows 10/11 Pro, Forge ne s'installe pas directement sous Windows : tout l'environnement de développement vit dans WSL (Windows Subsystem for Linux).

On active WSL, on installe la distribution Ubuntu 24.04, puis on travaille côté Linux — Python isolé via pipx, Node.js 20 pour la chaîne front (Tailwind), et MariaDB comme base de données avec un compte forge_admin.

VS Code se connecte à WSL via l'extension Remote WSL, et le projet reste sous ~/Projets/ (jamais sous /mnt/c/) pour de bonnes performances. Le guide ci-dessous détaille chaque étape.

Utiliser Forge pour créer une application

Utilisateur du framework — pipx

pipx installe Forge dans un environnement Python isolé, distinct du système et de chaque projet. Parcours principal recommandé.

Une fois pipx disponible, on installe le paquet officiel forge-mvc en pré-release — le flag --pre est requis tant que Forge est en bêta — puis on vérifie l'installation avec forge --version.

On génère ensuite un projet depuis un starter avec forge new et on le lance avec forge run.

Ne pas installer le paquet forge : c'est un projet différent, sans rapport.

Contribuer au framework

Développement du core

Pour travailler sur Forge lui-même : cloner le dépôt, installer l'environnement de développement, lancer les 5 validations canoniques avant commit.

On clone le dépôt avec git clone, on crée un environnement virtuel (python -m venv .venv) puis on installe les dépendances de développement via pip install -r requirements-dev.txt.

Une installation éditable depuis les sources (pas via pipx), qui inclut le runtime, les outils et les 7 modules opt-in du monorepo.

Avant chaque commit, on passe les 5 validations canoniques : pytest, compileall, ruff check, mkdocs build --strict et git diff --check.

Mode développement core
Déploiement encadré

Production — WSGI + Gunicorn + reverse proxy

En production publique, Forge expose son point d'entrée WSGI derrière Gunicorn et un reverse proxy comme Caddy ou Nginx. python app.py et forge run restent des outils de développement, pas d'exposition publique.

Le point d'entrée se déclare dans un fichier wsgi.py qui appelle create_configured_wsgi_app().

Puis on sert l'application avec Gunicorn (gunicorn wsgi:application --workers 4 --bind 127.0.0.1:8000), placé derrière un reverse proxy (Caddy ou Nginx).

À lire dans l'ordre : WSGI minimal, limites de production, puis le guide de déploiement complet.

Générer sans masquer.

Forge automatise les répétitions, mais les fichiers restent visibles, auditables et modifiables.

Chaîne de génération

1. Tout part d'un fichier JSON d'entité canonique, source unique du modèle.

2. La commande forge entity:validate vérifie le contrat avant toute génération.

3. Le SQL et les migrations demeurent visibles et lisibles.

4. Le modèle *_base.py est régénéré à chaque exécution.

5. Le modèle manuel, lui, est toujours préservé.

6. Le contrôleur, le formulaire et les vues CRUD sont ensuite échafaudés.

7. Il en résulte une application MVC claire et maintenable.

Le positionnement de Forge.

Ce que Forge est
  • +Plus structurant que Flask
  • +Moins massif que Django
  • +Moins API-first que FastAPI
  • +Plus explicite qu'un framework magique
  • +SQL visible par défaut
  • +Génération contrôlée et réversible
Ce que Forge n'est pas
  • -Pas un clone de Django, Symfony ou Laravel
  • -Pas un ORM complet imposé
  • -Pas une SPA React/Vue intégrée au core
  • -Pas une boîte noire qui cache le SQL
  • -Pas une plateforme SaaS multi-tenant
  • -Pas encore stable (bêta)
